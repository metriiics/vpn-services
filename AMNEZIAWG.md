# AmneziaWG 3.1 в Docker

Схема рассчитана на Ubuntu 24.04 VPS с публичным IPv4 и rootful Docker Engine. Базовый сервис публикует `1234/UDP`. Внутри контейнера `awg0` использует `10.77.38.1/24` и MTU `1280`. Проверьте, что `10.77.38.0/24` свободна на VPS и клиенте. Профиль клиента направляет IPv4 и IPv6 в туннель, сервер предоставляет выход в интернет по IPv4. IPv6 через этот профиль должен быть недоступен.

## Запуск

Нужны Docker Engine, Compose, доступ VPS к `/dev/net/tun` и разрешение `1234/UDP` во входящих правилах хостинга. На VPS скопируйте проект и выполните команды из его каталога. Подставьте фактический публичный IPv4 вместо `203.0.113.10`. [Установка Docker Engine и Compose на Ubuntu](https://docs.docker.com/engine/install/ubuntu/)

```sh
test -c /dev/net/tun
sudo install -d -o root -g root -m 0700 state
sudo docker compose config --quiet
sudo docker compose build --pull awg
sudo docker compose run --rm --no-deps init-profiles 203.0.113.10
sudo docker compose up -d --no-build --wait awg
sudo docker compose ps
```

Контейнер инициализации работает без сети. Он создаёт `state/profiles/server/awg0.conf` и `state/profiles/client.conf` с правами `0600` и отказывается перезаписывать существующие профили. Передайте клиентский `.conf` на устройство по доверенному каналу и импортируйте в приложение с поддержкой AmneziaWG 3.1. В рабочий контейнер монтируется серверный каталог. Защитите резервные копии `state/`. Следующие профили можно выдавать через веб-панель. [Клиенты AmneziaWG](https://docs.amnezia.org/documentation/amnezia-wg/#native-amneziawg-clients)

Сборка использует указанные в Dockerfile теги исходников и поддерживаемую ветку Alpine. На VPS достаточно Docker. В контейнере работает `amneziawg-go` в userspace, а `awg` загружает конфигурацию напрямую. Контейнер запускается с `NET_ADMIN`, доступом к `/dev/net/tun` и корневой файловой системой только для чтения. Пересылка, NAT и фильтрация находятся в сетевом пространстве контейнера. Правила запрещают клиентам обращаться к RFC 1918, CGNAT и link-local, в том числе к `169.254.169.254`. Административные сервисы VPS на публичных адресах защищайте отдельно. Docker может публиковать порт в обход правил UFW для входящего трафика хоста. Ограничения входящих портов проверяйте на уровне хостинга или в правилах пересылки Docker. [Сборка AmneziaWG](https://github.com/amnezia-vpn/amneziawg-go/blob/v3.1.20260828/Dockerfile) · [Docker и firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/)

## Административный доступ

Для SSH в firewall VPS задайте следующие входящие правила. `198.51.100.25/32` — пример. Подставьте фактический публичный IP, с которого администратор подключается к VPS.

| Сервис | Протокол и порт | Разрешённый источник |
| --- | --- | --- |
| SSH | TCP `22` или фактический порт SSH | IPv4 администратора с маской `/32`. Для фиксированного административного IPv6 задайте отдельный `/128`. |
| AmneziaWG | UDP `1234` | Сети клиентов. Если клиенты пользуются мобильными или меняющимися адресами, оставьте UDP доступным для всех IPv4. |

Сначала добавьте точное разрешение для SSH и проверьте новую сессию, затем удалите широкое правило доступа. Сохраните доступ к консоли хостинга на случай смены IP. Проверьте правила для обеих версий IP, если VPS доступен по IPv6.

## Веб-панель

Панель этого проекта управляет клиентами текущего AmneziaWG 3.1. Она открывается по HTTPS с разрешённого публичного IP. Caddy выпускает сертификат и запрашивает пароль после проверки IP. Внутренний порт панели `8080` доступен только в сети Docker. [Caddy и HTTPS](https://caddyserver.com/docs/quick-starts/https) · [Проверка исходного IP](https://caddyserver.com/docs/caddyfile/matchers#remote-ip)

1. Откройте `80/TCP` в firewall хостинга для проверки адреса Let's Encrypt и `443/TCP` для HTTPS. Запросы к панели с IP вне списка получат `403`. Если используете домен, направьте его запись `A` на VPS. В Cloudflare выберите **DNS only**, чтобы Caddy видел исходный IP.
2. Выполните команды ниже. Введите пароль по приглашению, затем вставьте полученный хэш в `.env` между одинарными кавычками. Укажите публичный IP VPS в `AWG_VPN_PUBLIC_IPV4` и публичный IP администратора с маской `/32` в `AWG_PANEL_ADMIN_IP`. Без `AWG_PANEL_DOMAIN` Caddy использует IPv4 VPS и запрашивает короткоживущий сертификат на IP. При наличии домена укажите его в `AWG_PANEL_DOMAIN` без схемы. [Сертификаты на IP](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability) · [Команда Caddy `hash-password`](https://caddyserver.com/docs/command-line#caddy-hash-password)

```sh
cp .env.panel.example .env
chmod 600 .env
sudo docker run --rm -it caddy:2.11.9-alpine caddy hash-password
```

Если VPN уже запускался со старой версией проекта, перенесите существующий серверный профиль перед обновлением. Для новой установки этот шаг пропустите.

```sh
sudo install -d -o root -g root -m 0700 state/profiles/server
sudo mv -n state/profiles/awg0.conf state/profiles/server/awg0.conf
```

Запустите сервисы из каталога проекта.

```sh
sudo docker compose -f compose.yaml -f compose.panel.yaml config --quiet
sudo docker compose -f compose.yaml -f compose.panel.yaml up -d --build --wait
```

Откройте `https://` с публичным IPv4 VPS или настроенным доменом и войдите как `admin`. Введите имя устройства и скачайте `.conf`. Панель выдаёт приватный ключ при создании файла. Если файл потеряется, отзовите профиль и создайте новый. Кнопка «Отозвать» удаляет доступ и сразу применяет изменение к AmneziaWG. Проверьте выпуск сертификата в логах `panel-https`, вход с разрешённого IP и ответ `403` из другой сети.

## Защита от утечек

| Где возникает утечка | Защита и остаточный риск |
| --- | --- |
| Обрыв, ручное отключение, запуск ОС, падение клиента | `AllowedIPs` действует при поднятом интерфейсе. Для защиты до запуска и после остановки нужен постоянный фильтр на устройстве. Проверяйте режимы обрыва и ручного отключения отдельно. |
| IPv6, более специфичные маршруты и обход по приложениям | Используйте `0.0.0.0/0, ::/0` и отключите исключения для приложений, сайтов и локальной сети. Фильтр должен блокировать прямой IPv6 так же, как IPv4. Приложение может интерпретировать профиль иначе, поэтому проверяйте захват на физическом интерфейсе. |
| DNS, несколько интерфейсов, DoH в браузере, Android Private DNS | `DNS = 1.1.1.1` задаёт системный резолвер, но отдельные приложения могут выбирать свой. Kill switch должен блокировать весь прямой IP-трафик, включая DoH на `443`, а не только DNS на `53`. Если требуется единый резолвер, настройте политику браузера и ОС и проверьте системные запросы и браузер отдельно. IP-адрес в `Endpoint` убирает необходимость в DNS для установления туннеля. |
| DNS после выхода из VPS | Системные запросы к `1.1.1.1` защищены на участке клиент → VPS. Обычный DNS после VPS идёт открыто. Если нужна конфиденциальность на этом участке, используйте DoH/DoT через туннель или отдельный резолвер с зашифрованным upstream. Доверие к выбранному резолверу и хостингу остаётся частью модели угроз. |
| WebRTC и браузерная идентификация | Проверьте ICE/STUN на физическом интерфейсе и на своей тестовой странице. Публичный адрес, обнаруженный через STUN, должен принадлежать VPS. Локальные ICE-кандидаты, cookies и отпечаток браузера требуют отдельных настроек, если нужно скрывать эти признаки от сайтов. |
| Наблюдение провайдера или хостинга | Локальный провайдер видит IP VPS, UDP, время, объём и размеры пакетов. VPS видит исходящий IP-трафик после снятия туннельного шифрования. Для содержимого прикладного трафика используйте HTTPS и другие протоколы со сквозным шифрованием. |

Профиль включает `HeaderProtectionKey`, случайное дополнение и переменные интервалы повторного рукопожатия. Сигнатуру `I1` подбирайте по результатам проверки из проблемной сети. Обфускация затрудняет классификацию, а доступность зависит в том числе от фильтрации IP VPS и UDP. Сравнение вариантов и порядок проверок описаны в [DPI.md](DPI.md). [Параметры AmneziaWG](https://docs.amnezia.org/documentation/amnezia-wg/) · [Подбор I1](https://docs.amnezia.org/documentation/instructions/amneziawg-signature/)

## Российские сервисы без VPN

Исключения настраиваются на клиенте. Выбранные сервисы увидят IP обычного подключения, остальные соединения по-прежнему должны использовать туннель. Это может улучшить доступ к сервисам, которые ограничивают IP дата-центров, и уменьшить объём трафика через VPS. Сетевые признаки самого туннеля сохраняются.

1. **Отдельный браузер на Windows или Android.** Импортируйте клиентский `.conf` в AmneziaVPN. В раздельном туннелировании приложений добавьте отдельный браузер в список программ, работающих без VPN. Все сайты, открытые в этом браузере, включая сторонние ресурсы страниц, будут использовать прямое подключение. Основной браузер оставьте вне списка исключений.
2. **Отдельные сайты в том же браузере.** В AmneziaVPN выберите режим «Адреса из списка не должны открываться через VPN». Добавляйте конкретные сервисы и проверяйте всю цепочку, включая вход, перенаправления и API. Например, для Госуслуг проверьте `gosuslugi.ru` и `esia.gosuslugi.ru`. AmneziaVPN сохраняет IPv4-адреса, полученные при добавлении домена. При изменении CDN список нужно обновлять. Если один IP обслуживает несколько сайтов, исключение затронет их все.
3. **Проверка.** При активном VPN сравните внешний IPv4 в основном и отдельном браузерах. Основной должен показывать IP VPS, отдельный — IP провайдера. Для исключений по сайтам подтвердите маршрут захватом трафика на физическом интерфейсе. Повторите тест с IPv6, при обрыве туннеля и после смены сети. Трафик, который должен идти через VPN, не должен переключаться на прямое подключение. Системный DNS и браузерный DoH проверяйте отдельно, если важно, чтобы DNS-запросы исключённых сервисов тоже шли напрямую.

Постоянный Linux kill switch из этого проекта блокирует прямой трафик и потому блокирует и эти исключения. Для строгого режима используйте полный туннель. Для режима с исключениями проверяйте поведение kill switch конкретного клиента при обрыве и ручном отключении. [Раздельное туннелирование AmneziaVPN](https://docs.amnezia.org/ru/documentation/instructions/vpn-split-tunneling/) · [Импорт профиля](https://docs.amnezia.org/documentation/instructions/connect-via-config/)

SOCKS5 внутри туннеля подходит для приложений, которым нужен прокси, и зависит от доступности AmneziaWG. Если в целевой сети блокируется UDP, XRay по TCP можно проверить как отдельный резервный способ подключения. Его доступность зависит в том числе от того, пропускает ли сеть соединения к выбранному IP. [SOCKS5 в Amnezia](https://docs.amnezia.org/documentation/instructions/socks5-proxy-server/) · [XRay в Amnezia](https://docs.amnezia.org/documentation/xray/)

### Настройки на устройствах

- **Linux с `awg-quick`.** Сохраните профиль как `awg-client.conf` и добавьте `FwMark = 0xa739` в `[Interface]`. Подставьте адрес VPS в [шаблон nftables](client-killswitch.nft.example). При необходимости выберите свободную метку и измените её в обоих файлах. Включите таблицу в постоянный ruleset, загружаемый до сети и независимо от запуска VPN. Проверьте синтаксис через `sudo nft -c -f /путь/к/файлу.nft`. Фильтр разрешает loopback, интерфейс `awg-client`, маркированный UDP к VPS и широковещательный DHCPv4. Смена порта или IP требует обновления правила. Проверяйте из локальной консоли, так как фильтр блокирует прямой IP-трафик, включая SSH. Шаблон рассчитан на клиентское устройство, которое не маршрутизирует трафик за другие устройства. [WireGuard и fwmark](https://www.wireguard.com/papers/wireguard-netdev22.pdf)
- **Windows.** В нативном AmneziaWG используйте один peer и оба маршрута `/0`, чтобы включить его фильтрацию. Для AmneziaVPN включите KillSwitch и проверьте, сохраняет ли установленная версия блокировку после завершения приложения, ручного отключения и перезагрузки. Если блокировка снимается, для этих сценариев нужен постоянный системный firewall. [Фильтрация в AmneziaWG для Windows](https://github.com/amnezia-vpn/amneziawg-windows-client/blob/master/docs/netquirk.md) · [KillSwitch AmneziaVPN](https://docs.amnezia.org/documentation/instructions/killswitch/)
- **Android.** В системных настройках VPN включите «Постоянная VPN» и «Блокировать подключения без VPN» для выбранного клиента. Уберите исключения по приложениям и проверьте переключение между Wi-Fi и LTE. [Android VPN lockdown](https://developer.android.com/work/dpc/network-telephony#always-on_vpn)
- **macOS и iOS.** На macOS проверьте KillSwitch AmneziaVPN. На iOS поведение зависит от реализации Network Extension и исключений системы. В том числе `includeAllNetworks` допускает системные исключения для DHCP и captive portal. Строгий режим нужно подтвердить для конкретного приложения и версии ОС. [KillSwitch AmneziaVPN](https://docs.amnezia.org/documentation/instructions/killswitch/) · [Маршрутизация VPN в Apple Network Extension](https://developer.apple.com/documentation/networkextension/routing-your-vpn-network-traffic)

## Приёмочные проверки

На VPS смотрите время рукопожатия и счётчики передачи. Healthcheck контейнера проверяет интерфейс и порт. Для проверки доступности и утечек нужен клиент в другой сети.

```sh
sudo docker compose exec awg awg show awg0 latest-handshakes
sudo docker compose exec awg awg show awg0 transfer
sudo docker compose exec awg nft list table inet amneziawg
```

1. **Подключение.** Внешний IPv4 должен совпадать с выходным IP VPS. Проверьте IPv6 через ресурс с AAAA и по адресу напрямую. IPv6-соединение должно завершиться ошибкой. Запустите HTTPS, QUIC и DNS-запрос к уникальному имени в контролируемой зоне, чтобы исключить ответ из кэша.
2. **Захват.** На физическом интерфейсе клиента или на тестовом шлюзе снимите `tcpdump`/Wireshark. Во время тестовых запросов за пределами туннеля ожидается UDP к VPS и предусмотренный клиентской ОС служебный трафик. Прямой IPv4/IPv6 к тестовому ресурсу, внешнему DNS или STUN считается утечкой. Тестовая страница и захват дополняют друг друга.
3. **Отказ.** Во время непрерывных тестовых запросов остановите VPS-контейнер командой `sudo docker compose stop awg`. Тестовый интернет-трафик должен прекратиться. Поднимите контейнер через `sudo docker compose up -d --wait awg` и проверьте восстановление. Повторите тест при остановке клиента, перезагрузке и смене Wi-Fi ↔ LTE. Для строгого режима любой успешный прямой запрос в этих сценариях означает, что настройку нельзя принимать.
4. **Изоляция.** С клиента проверьте попытку обращения к тестовому адресу в закрытой подсети. Доступ должен отсутствовать, а счётчик `restricted_ipv4` в цепочке `forward` должен увеличиться. Повторите проверки после обновления Docker-образа и клиента.
